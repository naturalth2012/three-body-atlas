# 执行方案：A 档英文可用化

> 决策依据见 [`I18N-DECISION.md`](I18N-DECISION.md)。本文是可执行的施工方案，
> 包含范围、步骤、每步的验收标准与风险处理。

## 目标

英文界面下，用户能**完整使用**三体模拟的全部功能，并读到英文的叙事与结论。
人物/剧情/地点/技术/术语的**描述**保持中文原文，并在界面上如实标注。

## 非目标（明确不做）

| 不做 | 原因 |
|---|---|
| 翻译人物档案（15,625 字） | 文学性文本，机翻会低于插件其余部分水准 |
| 翻译剧情节点（11,231 字） | 同上 |
| 翻译地点/技术/术语描述（9,455 字） | 同上 |
| 翻译 25 条 `verbatim` 原著台词 | 制造伪原著，版权与诚信双重问题 |
| 翻译时间线事件描述（5,615 字） | 同上 |
| 新增语言（日/韩等） | 无需求证据 |
| 改造 `locale/*.json` 结构 | 现有 NS 机制工作正常 |

## 核心设计：severity / kind 拆成稳定标识 + 显示文本

**这是本方案最大的技术风险，必须先处理。**

### 完整清单（已实测枚举，不可凭印象）

灾变的 `severity` 共 4 种取值：

| 现值 | 稳定 id | 触发点 |
|---|---|---|
| `致命` | `lethal` | 三日凌空（近距离） |
| `灼热` | `scorching` | 三日同现（远距离） |
| `极端` | `extreme` | 三日连珠 |
| `毁灭` | `devastating` | 行星被吞噬 / 潮汐撕裂 |

灾变的 `kind` 共 5 种取值：

| 现值 | 稳定 id |
|---|---|
| `三日凌空` | `tri-solar-day` |
| `三日同现` | `tri-solar-appearance` |
| `三日连珠` | `syzygy` |
| `行星被吞噬` | `planet-devoured` |
| `潮汐撕裂` | `tidal-disruption` |

### 依赖点（必须同步改，否则静默失效）

| 位置 | 代码 | 不改的后果 |
|---|---|---|
| `sim.js` L519 | `filter(c => c.severity === '毁灭' \|\| c.severity === '致命')` | 致命灾变筛不出，四角度解读永远说「没有致命天象」 |
| `sim.js` L559 | 同上（含 `'极端'`） | 「行星的处境」判定失效 |
| `client.js` L730-732 | CSS `.tba-catkind[data-severity='毁灭']` 等 3 条 | 灾变配色全丢 |

### 关键判断：kind 是多语义字段，只有一种要改

`kind` 在代码里承担三种互不相干的语义，**只有第三种需要改**：

| 用途 | 取值 | 是否改 |
|---|---|---|
| 天体类型 | `'planet'` / `'star'` | 否，已是英文标识 |
| 纪元类型 | `'stable'` / `'chaotic'` | 否，已是英文标识 |
| 灾变名称 | `'三日凌空'` 等 5 种 | **是** |

不加区分地全改会破坏天体绘制与纪元着色。改造时只碰灾变对象上的 `kind`。

### 改造方式

```js
// 生成时
{ kind: 'tri-solar-day', severity: 'devastating', text: '...' }

// 判断时
catastrophes.filter((c) => c.severity === 'devastating' || c.severity === 'lethal')

// 显示时（客户端 + 工具）
labelOfSeverity('devastating', lang) → '毁灭' / 'Devastating'
labelOfKind('tri-solar-day', lang)  → '三日凌空' / 'Tri-Solar Day'
```

**验收**：改造后 `simulate()` 返回的 `readings` 四角度文案与改造前**逐字一致**
（中文），致命灾变筛选数量不变，灾变配色不变。这三条都用自检断言钉住。

## 执行步骤

### 第 1 步：稳定标识改造（不改任何可见文本）

1. `sim.js` 里**灾变对象**的 `severity:` / `kind:` 改为稳定 id（5 种 kind、4 种 severity）。
   **不碰**天体 `kind`（`'planet'`/`'star'`）与纪元 `kind`（`'stable'`/`'chaotic'`）。
2. `sim.js` L519、L559 两处判断改用新 id。
3. `client.js` L730-732 的 3 条 CSS 选择器改用新 id。
4. 新增 `SEVERITY_LABELS`、`CATASTROPHE_KINDS` 映射表（zh/en 双语），导出。
5. `client.js` L2035-2037 渲染处改为查表显示；`index.js` 若引用同改。

**验收**：`selfcheck` 全过；`simulate()` 输出的中文文案与改造前完全一致
（用快照比对，不是肉眼）；灾变配色仍生效。

### 第 2 步：叙事双语化

把 `sim.js` 里 76 条成句中文、`engine.js` 里 42 条，改为
`{ zh, en }` 结构或 `t(zh, en)` 调用，由调用方传入 `lang`。

**设计选择**：不引入完整 i18n 框架。用最轻的形态——

```js
const L = (zh, en) => ({ zh, en })
const pick = (v, lang) => (lang === 'en' ? v.en : v.zh)
```

理由：叙事文案是**拼装出来的**（`'积分 ' + steps + ' 步'`），完整 i18n 的
占位符机制反而更难写。返回双语对象、由调用方挑选，最直接。

**兼容性**：`simulate(config)` 新增可选 `lang` 参数，默认 `'zh'`。
现有调用方（客户端、工具、自检）不传 `lang` 时行为不变。

**验收**：`simulate({...})` 不传 lang 时，返回结构与文案与改造前一致；
传 `lang: 'en'` 时所有叙述字段为英文且无残留中文（自检断言：英文字段不含
`/[\u4e00-\u9fa5]/`，专有名词如「三体」的括注除外）。

### 第 3 步：工具文案统一

`index.js` 里 10 条含中文的 `description` 改为纯英文（参数示例可保留中文
示例值，那是**输入样例**不是说明文字）。

**验收**：34 条 description 无中文，除 `e.g. 罗辑` 这类示例值。

### 第 4 步：语言透传与渲染

**不做逐处语言分支。** 实测客户端有 20+ 处直接渲染叙事字段
（`angle.text`、`civ.headline`、`c.verdict`、`data.verdict`…），逐处加
`lang === 'en' ? a.en : a.zh` 既繁琐又必然漏掉几处。

改为**在路由层一次性转换**：

1. `client.js` 的 `getJSON` helper（L533）自动附加 `lang` 字段，取值来自
   当前 locale。这样 16 处调用点**零改动**。
2. 路由 handler 收到 `lang` 后，调用 `simulate(config, lang)` 等，服务端直接
   返回目标语言。
3. 客户端渲染代码完全不动。

理由：叙事文本是服务端拼装的，服务端本来就该知道用哪种语言拼。让客户端
渲染 20 处双语对象，是把服务端的职责漏到 UI 层。

**例外**：灾变 `kind`/`severity` 的显示需要查表（第 1 步已建立映射），
客户端 L2035-2037 改两行即可，因为那里是 CSS `data-severity` 属性 + 文本，
必须在渲染时决定。

**验收**：语言为英文时，模拟面板不出现中文（专有名词括注除外）；
切回中文时恢复原文；16 处 `getJSON` 调用点均未改动。

### 第 5 步：市场条目与文档

1. `market-entry.yml`：10 → 11 个工具；补一句说明档案为中文原文。
2. `README.md`：说明英文覆盖范围（功能可用、档案为中文）。
3. `docs/ARCHITECTURE.md`：新增 i18n 策略小节。

### 第 6 步：自检与回归

新增断言：

| 断言 | 防的问题 |
|---|---|
| 稳定标识改造后中文文案逐字一致 | 拆 id 时改坏文案 |
| 致命灾变筛选数量不变 | `severity` 判断失效 |
| `lang:'en'` 时叙述字段无中文 | 漏译 |
| `lang` 缺省时行为不变 | 破坏既有调用方 |
| 34 条工具描述无中文 | 接口说明混语言 |
| 术语表译名一致（抽查 8 个） | 各处译名漂移 |

## 风险与对策

| 风险 | 对策 |
|---|---|
| 拆 `severity` 时漏改某处判断 | 已 grep 出全部依赖点（sim.js L519、L559；client.js L730-732 CSS），改完用断言钉住数量与配色 |
| 误改天体/纪元的 `kind` | 只改灾变对象上的 `kind`；天体 `'planet'/'star'` 与纪元 `'stable'/'chaotic'` 保持不动 |
| 叙事文案拼接导致漏译 | 自检扫 `lang:'en'` 输出里是否残留中文，不靠人工检查 |
| 破坏现有调用方 | `lang` 默认 `'zh'`，且第 1 步不碰文案 |
| 客户端 20+ 处渲染点漏改 | 改为路由层一次性转换，客户端零改动（第 4 步） |
| 译名不一致 | 术语表先定，自检抽查 |

## 方案审核结论

审核中发现并修正了三处问题，记录在此以免重复踩：

1. **遗漏 CSS 依赖**：原方案只提 `sim.js` 的两处逻辑判断，漏了
   `client.js` L730-732 三条 `[data-severity='毁灭']` CSS 选择器。不改则灾变
   配色全丢。
2. **误判 `kind` 单一语义**：`kind` 同时用于天体类型、纪元类型、灾变名称，
   只有灾变名称需要改。原方案「所有 `kind` 改为稳定 id」会破坏天体绘制与
   纪元着色。
3. **客户端渲染策略选错**：原方案打算在 20+ 处渲染点加语言分支，实际应在
   路由层一次性转换、客户端零改动。

另有两处**事实纠正**（写入 `I18N-DECISION.md` 前的初判有误）：

- 实体英文名并非缺失：人物 56/56、术语 37/37、地点 19/19、技术 24/24 **全部齐全**。
  缺的是英文**描述**。
- `QUOTES` 用的是 `textEn` 而非 `nameEn`，覆盖 5/30，其余 25 条是
  `verbatim: true` 的原著直引，本就不该翻。

## 验收标准（全部满足才算完成）

1. `node scripts/selfcheck.mjs` 全过，新增断言无一失败。
2. `simulate()` 中文输出与改造前**逐字一致**（快照比对）。
3. `simulate({lang:'en'})` 的叙述字段无残留中文。
4. 致命灾变筛选数量不变；灾变配色仍生效。
5. 25 条路由、11 个工具全部正常，`verify-routes` / `verify-guard` 通过。
6. `verify-pack` 通过。
7. 英文界面下模拟面板可用；档案区有「原文为中文」标注。
