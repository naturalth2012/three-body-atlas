# C 方案执行细节审核

逐条审核结论，全部经实测或读码确认。

## 细节 1：分批语义的正确基础

**问题**：`rng(seed)` 是 xorshift，只能顺序推进，不能跳到第 N 个样本。若每批新建 `rng(seed)`，第 2 批会重复第 1 批的样本。

**审核结论**：必须用「派生种子」——第 i 个样本用 `rng(seed ^ imul(i, 2654435761))` 独立初始化。实测确认：

- 同一 offset 重复调用结果完全一致（可复现）；
- `batch(0,6) ++ batch(6,12)` 与 `batch(0,12)` 逐项相同；
- 12 个样本无重复。

**注意**：派生方案的样本序列与「序列推进」不同。这是可接受的——普查不承诺与 `stabilityScan` 抽同一批初值，但**必须**在文档里说明两者用的是不同抽样，避免读者以为可以横向对比。

## 细节 2：性能与分批粒度

实测（steps=8000，含完整文明统计）：

| 批量 | 耗时 |
|---|---|
| 1 样本 | 25 ms |
| 6 样本 | 119 ms |
| 12 样本 | 193 ms |
| 24 样本 | 311 ms |

**审核结论**：`limit` 默认 12、上限 24。60 样本分 5 批，每批约 193 ms，客户端串行调用。总时长约 1 秒，每次请求都不超过 0.2 秒的阻塞，可接受。

**不做 worker**：DSH 宿主的 webServer handler 是同步执行的，引入 worker 需要额外的生命周期管理与打包配置，收益不足以抵消复杂度。分批已经解决了阻塞问题。

## 细节 3：剧透分级

**审核结论**：不需要。`sim.js` 全文不含 `spoiler`/`tier` 引用（实测 grep），模拟是物理计算，不描述剧情。现有 `/simulate`、`/stability` 也未做遮蔽。普查沿用同一口径。

**但有一条必须做**：普查的文案不能暗示"这就是三体文明的真实历史"。它是随机初值下的分布。

## 细节 4：数据形状

```js
{
  // 本批
  points: [{
    index,              // 全局样本序号，供客户端拼接
    generations,        // 文明代数
    stableEras, chaoticEras,
    stableSpan, chaoticSpan,   // 累计时长
    fatalEvents,        // 致命灾变数
    outcome,            // 'bound' | 'eject' | 'collapse'
    planetEscaped,      // 行星是否逃逸
    survived,           // 末帧剩余天体数
  }],
  // 聚合（仅 done 时给出，避免半成品被当成最终结论）
  aggregate: {
    samples, histogram: {0:n,1:n,...}, mean, median, max,
    byOutcome: {bound:{n,mean}, eject:{...}, collapse:{...}},
    correlation,        // 恒纪元累计时长 vs 代数 的皮尔逊系数
    verdict,            // 一句话结论
  },
  done: boolean,
  next: number | null,  // 下一批的 offset
}
```

**审核结论**：`aggregate` 只在 `done` 时返回，这是刻意的——半成品的均值容易被误读为结论。

## 细节 5：i18n

**审核结论**：文案在 `client.js` 的两套内联字典（zh 约 L200–400、en 约 L380–500）。新增键必须两处都加，否则 `t()` 回退到键名，界面会出现 `censusIntro` 这种原文。自检需断言两套字典键集一致。

## 细节 6：路由与工具

- 路由：`CENSUS_PATH = BASE + '/census'`，用 `registerAction`（POST）。理由是参数含 offset/limit，且客户端要串行调用多批。
- 跨站防护：`actionHandler` 已统一调用 `isCrossSiteRequest`，**无需额外代码**。但自检要加一条 `/census` 的跨站断言，防止将来有人把它注册成裸路由。
- 参数夹取：`samples` 8–120，`offset` 0–120，`limit` 1–24。超出即夹取，不报错（与现有路由一致）。
- Agent 工具：新增 `three_body_census`，参数 `samples`（默认 30）。返回文字摘要 + 直方图。

## 细节 7：客户端视图

放在"模拟"页第 3 个子标签"稳定性普查"**之后**，新增"文明史普查"。理由：二者是姊妹功能，放在一起符合直觉。

交互：一个运行按钮 → 循环 POST `/census`，每批 12 个 → 进度条"已采样 24/60" → 完成后展示直方图 + 结局分布 + 指标卡 + 散点。

**关键约束**：循环必须有上限保护（`while (!done && guard < 40)`），否则路由若因 bug 永远返回 `done: false`，浏览器会无限请求。

## 细节 8：验收与回归

必须同时满足：

1. 自检全过（现有 658 项 + 新增）；
2. `/census` 分批拼接 == 一次性全量；
3. 聚合数学自洽（直方图总和 == 样本数）；
4. **单次 `/simulate` 行为未变**——这是回归红线，因为 C 方案的前提就是"不动单次模拟"；
5. `/census` 跨站被拒；
6. 打包后自检仍全过。

## 已排除的方案

- **修改 `simulate` 默认时长**：实测 T=19 时代数峰值 4，之后衰减到 1，拉长无益。
- **行星逃逸后重新注入**：实测能把累计代数从 4 提到 7，但那是分段积分拼接，**不是一条连续轨迹**。若要用，必须明确标注为"多次独立积分的累计"，且不能与单次模拟混为一谈。本方案不采用，避免混淆。
- **改文明计数口径**：实测「恒纪元数」1.50、「致命灾变数」0.50、「纪元段数」2.50，都只有个位数。换口径解决不了量级问题，根因是积分时长与行星逃逸。
