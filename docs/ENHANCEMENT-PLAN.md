# 第一项：大低谷事件补全

## 1.1 需求分析

**问题**：大低谷纪元覆盖「危机纪元 20 – 80 年」，跨度 60 年，是全书写跨度最长的单一纪元之一，却只有 1 个事件。相邻的 pre-crisis 有 11 个、crisis 有 15 个。时间线读者点进这个纪元，只看到一条，会以为这里"没什么事发生"——而实际上这是三部曲最惨烈的人类自我毁灭段落。

**现有那一条**（`great-ravine`）是**概括式**的：它把起因、过程、结果全压在一段 200 字里，还顺手讲了"给岁月以文明"和技术爆炸。这不是错，但它替代不了分点叙述——一个大跨度纪元需要**多个锚点**才能让读者感到时间在流动。

**目标**：让大低谷从 1 个事件变成 5 个，每个承担不同的叙事职能，且与已有那条不重复。

**边界**：
- 只补 `EVENTS`，不改 `ERAS` 的定义
- 新事件的 `era` 必须是 `great-trough`
- 引用的人物 id 必须已存在（自检会验）
- 不虚构原著没有的情节；拿不准的细节用概括表述，不编造具体数字

## 1.2 详细执行方案

补 4 条，与原有一条合计 5 条，按时间顺序覆盖 60 年：

| # | id | 时间锚点 | 叙事职能 |
|---|---|---|---|
| 1 | `great-trough-trigger` | 危机纪元 20 年前后 | **起因**：战时经济体制、配给制、环境与农业崩溃 |
| 2 | `great-ravine`（已有） | 危机纪元 20–80 年 | **概括**：人口从 80 亿到 8 亿 |
| 3 | `great-trough-darkest` | 危机纪元 40 年前后 | **谷底**：集体绝望、逃亡主义、秩序崩解 |
| 4 | `give-years-to-civilization` | 危机纪元 60 年前后 | **转折**：「给岁月以文明」口号的提出与被接受 |
| 5 | `great-trough-revival` | 危机纪元 80 年前后 | **复苏**：第二次启蒙、技术爆炸的土壤 |

```js

  era: 'great-trough',
  year: '危机纪元 20 年前后',
  title: '...',
  desc: '...',            // 80–160 字，具体但不编造
```

**人物引用**：只用已存在的 id。可用的有 `luo-ji`、`shi-qiang` 等；「给岁月以文明」那条不指定具体人物（原著中这是群体转向，不是某人的台词）。

**验证方式**：
1. `selfcheck` 的事件引用完整性断言必须通过
2. 新增断言：`great-trough` 纪元的事件数 ≥ 4

## 1.3 审核方案

**这个方案有没有问题？**

*问题一：会不会编造原著没有的细节？*
这是最大风险。大低谷在书中的描写是**侧写**——通过罗辑冬眠醒来后的对话、通过"给岁月以文明"这个口号带出，没有编年史式的细节。所以我不能写"某年某月发生了某暴动"。

**修正**：`desc` 一律用**概括性表述**，不写具体人名地名事件名。时间锚点用"前后"而非精确年份。这一点必须写进实施规范。

*问题二：`importance` 怎么定？*
原有那条是 3（最高）。新补的 4 条如果也都是 3，就等于把大低谷抬到和"黑暗森林打击"同级，不合适。

**修正**：起因和谷底用 2，转折和复苏用 2，只有原有那条概括保持 3。

*问题三：会不会与原有那条内容重叠？*
原有那条已经讲了起因（"为支撑太空军备与地球经济被榨干"）和结果（"技术爆炸"）。

**修正**：新补的起因条要**展开**原有那句，而不是重复；转折条聚焦口号本身的社会心理，不重复人口数字。实施后要逐条比对，确认没有句子重复。

**审核结论**：方案可行，但必须遵守三条约束——不编造细节、importance 不越级、不与原条重复。已写入 1.2 的验证方式。

# 第二项：导出与复制为 Markdown

## 2.1 需求分析

**问题**：仓库里完全没有 `clipboard` / `download` / `toBlob`。16 个标签页、30 条引文、247 条关系、56 份人物档案，读者看到有价值的内容**带不走**。这是纯粹的只读型面板。

**为什么值得做**：这是所有改动里「投入最小 / 感知最强」的一项。读者最可能的动作是「把罗辑的档案发给我朋友」或「把这条引文贴进笔记」，而现在只能截图。

**目标**：给每个内容区块一个「复制为 Markdown」入口，输出结构化的、可直接粘贴的文本。

**边界**：
- 不引入新依赖（无构建步骤，必须手写）
- 不新增路由（纯客户端功能，数据已在内存）
- 不改变现有布局，只在已有区块加一个按钮
- 必须双语：中文界面输出中文标题，英文界面输出英文

## 2.2 详细执行方案

**设计原则**：复制的是**当前视图的内容**，不是原始数据。读者看到的筛选、剧透遮蔽都要体现在输出里。

### 2.2.1 核心工具函数

```js
// 一个通用的复制入口：写剪贴板 + 降级 + 反馈
async function copyMarkdown(text, label) { ... }
```

**降级链**：`navigator.clipboard.writeText` → `document.execCommand('copy')`（旧 WebView / 非安全上下文）→ 失败时弹出可选中的文本框让用户手动复制。

DSH 桌面版的 WebView 是 `http://127.0.0.1`，**属于安全上下文**，`navigator.clipboard` 可用。但降级仍要写，因为无法保证所有宿主环境。

### 2.2.2 各区块的 Markdown 输出格式

| 区块 | 输出 | 优先级 |
|---|---|---|
| 人物详情 | `# 名称` + 别名/阵营 + summary + details + fate + 关系列表 | 高 |
| 引文 | `> 引文正文` + `—— 说话者` + 出处 + 语境 | 高 |
| 关系图 | 邻接列表（节点 + 边，含关系标签） | 中 |
| 时间线 | 按纪元的 `## 纪元名` + `- 年份 标题` | 中 |
| 关系路径 | `A —[关系]→ B —[关系]→ C` | 中 |
| 模拟报告 | 参数 + 结论 + 灾变列表 | 低 |

**格式示例**（人物）：

```markdown
# 罗辑

**别名**：面壁者、执剑人
**阵营**：地球 / 人类
**首次出场**：《黑暗森林》

面壁者中最不情愿的一个……

## 命运
……

## 关系
- **庄颜**（爱人）：……
- **史强**（搭档）：……
```

### 2.2.3 实现方式

不新增组件，而是在**已有渲染函数里**插入按钮。需要先找到各区块的渲染入口。

**已知约束**：`client.js` 是单文件 3136 行、40 个组件。改动要**局部化**，不能重构。

### 2.2.4 验证方式

1. 自检断言：`client.js` 里存在 `copyMarkdown` 与至少 3 个调用点
2. 自检断言：剪贴板 API 有降级分支（`execCommand` 出现）
3. 自检断言：Markdown 输出函数是纯函数（可在 Node 里测），导出为 `__test__`
4. 单元测试：给一个已知人物，断言输出包含 `# 名称`、关系列表、命运段
5. 双语测试：同一人物在 `zh` / `en` 下的标题不同

**关键设计决定**：把 Markdown 生成写成**纯函数**并从 `client.js` 导出，这样能在 Node 里直接测，不必开浏览器。这是第一项里 `routeTable()` 的同一思路。

## 2.3 审核方案

**这个方案有没有问题？**

*问题一：`client.js` 是模块工厂，能导出纯函数吗？*
`client.js` 通过 `window.__ModuleLoader__.load({...})` 注册，不是普通 ESM 模块。直接从 Node import 会失败。

**这是真问题，而且我最初的备选方案也不对。**

- **A**：在 `client.js` 里写函数，另复制一份到 `scripts/markdown.mjs` 供测试 —— 两份实现必然漂移，**不可接受**
- **B**：正则提取 + eval（沿用 selfcheck 的 `grabArrow`）—— 但 `grabArrow` 只配平 `{}`，Markdown 生成必然用模板字符串，`${...}` 里的花括号会让它**失配**。**不可靠**

**实测找到了 C 方案**：`client.js` 能在 Node 里执行。它的结构是

```js
window.__ModuleLoader__.load({ factory(require) { ... return { inject, apply } } })
```

`require` 只用到 `react` 一个依赖。用 `vm` 建一个沙箱、stub 掉 `window` 和 `react`，就能捕获 factory 并执行它，拿到返回对象。

于是：**把 Markdown 生成器挂在返回对象的 `__test__` 上**，客户端照常用，Node 测试直接 import。单份实现，没有漂移，也不用脆弱的正则。

已实测验证（`_probe_factory.mjs`）：脚本执行成功、捕获到 load、factory 返回 `{ inject, apply }`。

*问题二：复制按钮会不会破坏现有布局？*
按钮要插进已有 DOM 结构，可能影响 flex 布局。

**修正**：用绝对定位的小按钮，或放进已有的 header 行。实施时先看每个区块的实际结构再定，不预先假设。

*问题三：剪贴板在 DSH WebView 里真的可用吗？*
不确定。

**修正**：实施后**必须在真实面板里点一次**。这是第二项唯一的不可自动化验证点。

*问题四：输出格式要不要包含剧透内容？*
读者可能在剧透遮蔽状态下复制。

**修正**：复制当前**可见**内容，遮蔽的字段输出 `[已按剧透层级遮蔽]`。与「复制当前视图」原则一致。

**审核结论**：方案可行。C 方案（vm 沙箱 + `__test__` 导出）已实测验证，取代了原定的 B 方案。剩余风险是剪贴板可用性，只能真机验证。

## 2.4 实施记录

**新增纯函数**（在 `client.js` 的 Drawer 段之前）：

|---|---|

**UI**：Drawer 的关闭按钮旁加了 `.tba-drawer-copy`，`float:right` 与关闭按钮并排，
不挤占标题。点击后 1.6 秒内显示「已复制」或「复制失败」。

**过程中修掉两个真 bug**：

1. **关系显示成 id**（`**zhuang-yan**` 而不是 `**庄颜**`）。原因是我在测试里传了
   `data/index.js` 的模块导出（`CHARACTERS` 大写），而面板收到的是 `bundle()`
   的形状（`characters` 小写）。**代码本身是对的，测试传错了对象**——但这暴露了
   一个真实风险：两种数据形状同名不同键，很容易在别处也搞混。已在自检里用
   `bundle` 形状的注释标出。

2. **`document.body.appendChild` 断言冲突**。原断言 `client.js 不向 body 追加第二个应用`
   用的是方法名匹配，而剪贴板降级需要临时 textarea。**断言比意图更宽**。
   已改为匹配真正的建根模式（`createRoot(`、`.render(h(`、`appendChild(*root)`），
   这样既不放过真问题，也不误伤合理的降级路径。

**新增自检**（14 项）：沙箱执行 factory、`__test__` 存在、四种档案形状、关系名解析、
遮蔽条目不泄露正文、时间线分组与计数、剪贴板降级路径存在。

# 第四项：改编三栏对照

## 4.1 需求分析

**现状**：`DIFFERENCES` 有 16 条，每条已经天然是「原著 / 影视 / 影响」三段：

```js
{ topic, media, book, screen, impact }
```

分布：腾讯剧集 4、Netflix 9、动画 3。

**问题**：现在它们只是**列表**——一条一条读，读第 5 条时已经忘了第 1 条怎么改。
而改编对照的价值恰恰在**横向比较**：同一个场景，三种处理方式并排放着，差异自己就跳出来了。

**这是三体插件最该有、而别的知识库做不出来的功能**：它有原著、有腾讯剧集、
有 Netflix、有动画，四份文本可以互相照。一个通用的知识库没有这个素材。

**目标**：把差异列表改造成可横向对照的视图——选一个媒体，看它与原著逐条并排。

**边界**：
- 不新增数据（16 条已够，缺的是呈现方式）
- 不改数据结构（`book`/`screen`/`impact` 三字段已够用）
- 保留现有列表视图（有人就喜欢顺着读）

## 4.2 详细执行方案

### 4.2.1 交互设计

**两栏对照**（不是三栏）——这是关键的取舍。

理由：`impact` 不是第三种"呈现"，而是对前两栏差异的**评论**。把它做成第三栏
会让人误以为它是"另一个版本"。正确的位置是两栏下方的横条。

```
┌─────────────────┬─────────────────┐
│  原著            │  腾讯剧集        │
│  （book 全文）    │  （screen 全文）  │
├─────────────────┴─────────────────┤
│ 差异的代价：impact                  │
└───────────────────────────────────┘
```

**媒体切换**：顶部三个 chip（腾讯 / Netflix / 动画），选中一个后，列表只显示
该媒体的条目，并按主题并排。

### 4.2.2 组件结构

不新建标签页（已有 16 个，够多了），而是**改造现有 `DiffTab`**：

- 顶部：媒体筛选 chip + 视图切换（列表 / 对照）
- 列表模式：保持现状
- 对照模式：每条一个卡片，两栏 + 底部影响条

### 4.2.3 响应式

窄屏时两栏改为上下堆叠。用现有 CSS 断点风格（`@media`），不引入新机制。

### 4.2.4 验证方式

1. 自检：`DiffTab` 有视图切换状态
2. 自检：两栏渲染引用 `book` 与 `screen`，影响条引用 `impact`
3. 自检：媒体筛选生效（选中 Netflix 时只渲染 media 为 Netflix 的条目）
4. 自检：列表模式仍存在（回归）
5. 人工：真实面板里切换视图与媒体

## 4.3 审核方案

*问题一：两栏会不会比三栏信息更少？*
不会。`impact` 在底部横条里同样可见，且语义更准确。

*问题二：改造现有 `DiffTab` 会不会破坏它？*
有风险。`DiffTab` 已有筛选逻辑。

**修正**：保留原列表视图作为默认，新视图是**增量**，不是替换。这样即使新视图
有问题，读者仍能用旧的。

*问题三：媒体筛选与现有筛选会不会冲突？*
需先看 `DiffTab` 现有的状态。

**修正**：实施前先读 `DiffTab` 全文，确认现有筛选维度，避免加重复状态。

*问题四：窄屏两栏会不会挤？*
会。

**修正**：加 `@media (max-width: 720px)` 改为单列堆叠。这个断点值要先看现有 CSS 有没有约定。

**审核结论**：可行。关键约束是**增量而非替换**、**先读现有实现再动手**。

## 4.4 实施记录

**改造现有 `DiffTab`，不新建标签页**（已有 16 个，够多了）。

**两栏而非三栏**——这是方案审核时就定下的：`impact` 是对差异的评论，不是
第三种"版本"。做成第三栏会让人误读。

```
┌──────────────┬──────────────┐
│ 原著 (book)   │ 影视 (screen) │
├──────────────┴──────────────┤
│ 影响 (impact) ← 底部横条      │
└─────────────────────────────┘
```

**增量而非替换**：`view` 状态默认 `'list'`，保持原有逐条视图；点「并排对照」
才切换。即使新视图有问题，读者仍能用旧的。

**实现要点**：
- 复用现有 `media` 筛选状态，没加重复维度（方案 4.3 问题三）
- 视图切换按钮并入现有 chips 行，不新增工具栏

- `.tba-one` 单列容器，避免 grid 里嵌 grid

**新增自检**（13 项）：默认列表视图、两种卡片构造、视图切换选择、
两栏结构、影响条位置、媒体筛选仍在、CSS 单列与窄屏断点、双语键、
16 条差异字段完整。

# 第六项：阅读进度与自动剧透

## 6.1 需求分析

**现状**：剧透分级已经存在（`MAX_TIER`、`TierPicker`、`maskRecord`），但它是一个
**手动开关**——读者每次打开面板都要自己选一次层级。

**问题**：这个设计假设读者记得自己的进度。实际上：
- 每次打开都要重选，很容易忘记（然后就看不到内容，或看到不该看的）
- 没有"我读到第二部第三章"这种表达方式
- 层级是全局的，但读者可能同时在不同作品里处在不同进度

**目标**：让读者记录一次阅读进度，面板据此自动设定剧透层级。

**边界**：
- 复用现有 `MAX_TIER` 与 `maskRecord`，不新建遮蔽机制
- 进度存在本地（`localStorage`），不上传、不入库
- 保留手动覆盖（读者可以临时调高/调低）

## 6.2 详细执行方案

### 6.2.1 进度模型

不按"第几章"（章节划分在不同版本里不一致），按**作品完成度**：

```js
{ three-body: 'done', 'dark-forest': 'reading', 'deaths-end': 'unread' }
```

三档：`unread` / `reading` / `done`。

### 6.2.2 层级推导

```
最高已开始的作品 → 对应 tier
  unread  → 不提升
  reading → 该作品 tier
  done    → 该作品 tier（读完即可看全部）
```

`tierOfWork` 已经存在，直接复用。

### 6.2.3 存储

复用现有 `readPref` / `writePref`（client.js 已有 localStorage 封装）。

### 6.2.4 UI

在 `TierPicker` 旁边加一个「阅读进度」入口，点开是三行作品选择。

### 6.2.5 验证方式

1. 自检：进度推导函数是纯函数，可从 `__test__` 测
2. 自检：`unread` 不提升层级
3. 自检：`done` 给出该作品的最高层级
4. 自检：手动覆盖仍优先生效
5. 自检：进度只写 localStorage，不发网络请求

## 6.3 审核方案

*问题一：进度与手动层级谁优先？*
如果进度自动覆盖手动选择，读者会困惑"为什么我调了又变了"。

**修正**：手动选择**优先**，且一旦手动调整就标记为"手动模式"，直到读者
明确回到"跟随进度"。这是最小惊讶原则。

*问题二：按作品粒度够不够？*
读者可能读到《黑暗森林》一半。

**修正**：`reading` 状态本身就表示"读到一半"，层级给该作品的 tier 即可。
再细分需要章节数据，而章节划分跨版本不一致——**不做**，并在文档说明为什么。

*问题三：localStorage 在某些宿主不可用？*
可能（隐私模式）。

**修正**：`readPref` 已有 try/catch，失败时退化为"不记忆"，功能仍可用但每次要选。

**审核结论**：可行。关键是**手动优先**、**按作品粒度**、**存储失败可降级**。

## 6.4 实施记录

**纯函数** `tierFromProgress(progress)`：读 `{ 'three-body': 'done' }` 这样的映射，
返回该解锁的层级；无进度返回 `null`（让调用方保持手动值）。

**手动优先**（方案 6.3 问题一的处置）：
- 手动调层级 → 写 `tba:tier-manual = '1'`
- 选「跟随进度」→ 写 `'0'` 并立即应用推导值
- 手动模式下界面显示「已手动设定层级 · 改为跟随进度」

**为什么按作品不按章节**（方案 6.3 问题二）：章节划分跨版本、跨译本不一致，
「第 12 章」对不同读者不是同一处。`reading` 状态本身就表达"读到一半"，
层级给该作品的 tier 即可。自检里加了断言禁止引入章节粒度。

**一个实现细节**：`WORK_TIER` 在 `data/spoiler.js`，客户端无法 import，
所以在 client.js 里镜像了一份（只含三个主作品）。这是**有意的重复**，
注释里写明了原因——不是疏忽。

**新增自检**（18 项）：`tierFromProgress` 导出、未读不提升、在读/读完解锁、
取最高、顺序无关、未知 id 忽略、手动标记的写入与清除、界面提示、
不发网络请求、只读写本地偏好、不引入章节粒度。

# 第七项：闪卡自测

## 7.1 需求分析

**现状**：11 个 agent 工具全是查询型（`three_body_search`、`detail`、`ask`…）。
读者问"罗辑是谁"，工具答；但读者**没法检验自己记不记得**。

**为什么值得做**：知识库的价值不止"查得到"，还有"学得进"。三体的人物、术语、
技术数量正好在可背诵的规模（56 / 37 / 24），做成闪卡是自然的学习闭环。

**目标**：从现有数据自动生成问答卡，让读者自测。

**边界**：
- 不新增数据——题目从 `summary`、`term`、`faction`、`tech` 等已有字段生成
- 不做间隔重复算法（那是另一个量级的工程），只做"抽一张、答、看对错"
- 不新增路由（纯客户端，数据已在内存）

## 7.2 详细执行方案

### 7.2.1 题目类型

从现有字段生成三类：

| 类型 | 生成方式 | 例 |
|---|---|---|
| 人物辨认 | `summary` 作题干，四个 `name` 作选项 | "太空军政委，用一生伪装执行一个判断……" → 章北海 |
| 术语释义 | `definition` 作题干，四个 `term` 作选项 | "宇宙中任何暴露坐标的文明……" → 黑暗森林法则 |
| 技术归属 | `tech.summary` 作题干，四个 `name` 作选项 | 同上 |

### 7.2.2 干扰项选择

**关键设计**：干扰项不能随机，否则题目会变得可笑（"罗辑"的干扰项是"歌者"）。
按同 `faction` 或同 `category` 优先取，不足再放宽。

### 7.2.3 交互

- 一次一张：题干 + 四个选项
- 点选后立即标对错，并给出正确项
- 累计正确率（本局），可重置
- 剧透层级生效：高于当前层级的条目不出题

### 7.2.4 验证方式

1. 自检：`buildCards` 是纯函数，可从 `__test__` 测
2. 自检：每题恰好 4 个选项，正确答案在其中
3. 自检：干扰项与正确答案不同
4. 自检：剧透层级生效（层级 1 时不出第三部的题）
5. 自检：选项去重

## 7.3 审核方案

*问题一：自动生成的题目会不会有歧义？*
`summary` 里可能包含人名，等于泄题。

**修正**：生成题干时**剔除正确答案的名字**，若剔除后题干太短（<15 字）则跳过该条。
这条必须写进实现，否则题目会自我泄露。

*问题二：干扰项同阵营优先，会不会泄露答案？*
如果四个选项同阵营，读者可以靠排除法。但反过来，跨阵营的干扰项太离谱。

**修正**：同类别优先取 2 个，再从全体取 2 个。兼顾合理与不泄露。

*问题三：正确率统计要不要持久化？*
如果持久化，读者会为了分数焦虑。

**修正**：只存本局，刷新即清零。**这是有意的**——闪卡是自测工具，不是考试。

*问题四：会不会题量太少？*
56+37+24 = 117 条，但部分 summary 短或不适合出题。

**修正**：先实现，再量实际可出题数；若 < 30 条则考虑放宽题干条件。

**审核结论**：可行。关键约束是**题干剔除答案名**、**干扰项混合策略**、**只存本局**。

## 7.4 实施记录

**`buildCards(data, maxTier)` 纯函数**，从三类数据自动出题：
人物 59 + 术语 37 + 技术 24 = **120 张**（maxTier=3）。

**两条防泄漏规则**（方案 7.3 问题一的处置）：
1. 题干用 `split(name).join('＿＿')` 剔除答案名
2. 剔除后正文 < 15 字则跳过该条（说明名字占了句子大半）

实测 120 张里 **0 张题干含答案**。

**干扰项混合策略**（问题二的处置）：同阵营/同类别优先。原实现是「同类取 2 +
全体取 1」，最终审核时发现**第 3 个选项经常荒谬**——汪淼的选项里出现「秦始皇」。
改为**同类取满 3 个**，不足时才放宽。同阵营比例从 67% 提升到 **95%**（165/174）。

**第二个干扰项问题**：「秦始皇」的 `kind` 是 `'游戏投影'`——三体游戏里的 NPC
化身，不是故事里的人物。用它当人物题的答案或干扰项都不成立。已排除该类条目。

**实施中发现并修掉的真 bug**：`maxTier` 一开始没生效——`maxTier=1` 时仍是
120 张，第三部人物照样出题。原因：**记录上没有 `tier` 字段**，`bundle` 也不按
tier 过滤（遮罩是客户端做的）。改为从 `works` + `firstWork` 经 `tierOfWork`
推导。修复后 maxTier=1 → 86 张，第三部人物被排除。

**成绩只存组件状态**（问题三的处置）：`useState` 而非 `localStorage`，
自检里有断言禁止 `writePref` 写入成绩。

**新增自检**（19 项）：`buildCards` 导出、题量下限、四选项不重复、
答案在选项内、**题干不含答案**、题干够长、三类题目都有、层级过滤生效、
层级 1 不考第三部、可复现、成绩不持久化、独立标签页、双语键。
